# 2026-05-17 API 管理右键新建分组设计

## 背景

当前 API 管理页的单个 API 卡片支持右键“切换分组”，但现有实现只展示已有分组列表，无法在该菜单内直接输入一个新的分组名。实际使用中，这会迫使用户先去顶部或其他入口创建分组，再回来给单个 API 切换分组，路径过长。

当前仓库还有两个待发布本地提交：

1. `2dd2e00` `feat: selectively sync upstream v0.6.16 fixes`
2. `a9de80b` `docs: tighten README desktop positioning`

本次改动应作为第三个独立提交落在这两个提交之后，保持“功能同步 → README 修正 → 使用中发现的交互补丁”的发布顺序。

## 目标

在 API 管理页中，对某个 API 卡片右键打开“切换分组”菜单时：

- 菜单顶部直接提供一个输入框；
- 用户可以输入一个新的分组名并按 `Enter`，立即把当前 API 切换到该分组；
- 仍然保留已有分组列表，支持直接点选；
- 不修改数据库 schema，不新增独立分组表，继续沿用现有 `group_name` 字段语义。

## 非目标

- 不重做 API 卡片布局；
- 不把右键菜单改成独立弹窗；
- 不新增“批量新建分组”能力；
- 不改动顶部“添加分组”“迁移本组模型”等既有工作流；
- 不改变发布顺序，不重写已有两个 commit。

## 现状分析

当前实现位于 `src/features/pool/PoolManager.tsx`：

- `CardBody` 内使用 `groupMenu` 控制右键菜单显示；
- 菜单内容位于 `src/features/pool/PoolManager.tsx:476-507` 附近；
- 现在只渲染 `groupOptions.map(...)`，所以只能展示已有分组；
- `handleGroupChange()` 位于 `src/features/pool/PoolManager.tsx:896-898`，本质上调用 `adapter.pool.updateGroup(id, groupName)`；
- 顶部分组栏的本地顺序、迁移和重命名逻辑已经存在，可复用当前 `normalizeGroupName()`、`sortGroups()` 和 query invalidation 机制。

这说明问题不在后端，也不需要改接口；瓶颈纯粹是前端右键菜单没有提供“输入新分组名”的入口。

## 方案对比

### 方案 A：右键菜单顶部直接加输入框（推荐）

在现有菜单顶部加入输入框，用户输入后按 `Enter` 直接切换；下面保留已有分组列表。

**优点：**
- 路径最短，符合用户要求；
- 对现有结构侵入最小；
- 可复用已有 `Input`、`handleGroupChange()` 和列表渲染逻辑。

**缺点：**
- 需要在右键菜单内部补少量键盘与焦点处理。

### 方案 B：菜单项里点“新建并切换分组”再弹小对话框

**优点：** 交互显式。  
**缺点：** 多一步，打断右键菜单的直接操作路径，不符合当前诉求。

### 方案 C：输入框只做筛选，额外渲染“切换到新分组 xxx”动作

**优点：** 语义明确。  
**缺点：** 逻辑更绕，收益不高。

**推荐结论：** 采用方案 A。

## 设计

### 1. 交互设计

在 API 卡片右键菜单顶部增加一个小输入框，放在“切换分组”标题下方、已有分组列表上方。

行为定义：

- 右键打开菜单时，输入框默认清空；
- 占位文案使用中文，例如：`输入新分组后回车`；
- 输入非空内容后按 `Enter`：
  - 若输入值经 `trim()` 和 `normalizeGroupName()` 后与当前分组不同，则立即调用 `onGroupChange(entry, normalized)`；
  - 若输入值恰好等于已有分组名，也按正常切换处理；
- 按 `Escape`：关闭菜单；
- 点击已有分组项：保持当前行为不变；
- 当前分组在列表中继续高亮。

### 2. 状态设计

在单个 API 卡片的 `CardBody` 中新增一个本地输入状态，例如 `groupDraft`：

- 生命周期与该卡片右键菜单绑定；
- 菜单关闭时清空；
- 打开新菜单时重新开始，不保留旧输入。

不引入跨卡片共享状态，避免多个卡片右键时状态串扰。

### 3. 数据流设计

提交新分组时继续复用已有数据流：

1. 前端从输入框拿到字符串；
2. 调用 `normalizeGroupName()` 规整；
3. 走 `handleGroupChange(entry, group)`；
4. `handleGroupChange()` 调用 `updateGroupMutation.mutate({ id, groupName })`；
5. 成功后刷新 entries；
6. 额外补一轮 `queryClient.invalidateQueries({ queryKey: ["groups"] })`，确保新分组标签立即出现在顶部。

这里不需要新增后端命令，因为后端已经允许把 `group_name` 更新为任意字符串。

### 4. 边界与约束

- **空输入不提交。**
  - 虽然 `normalizeGroupName()` 会把空值规整成 `auto`，但在“创建新分组”的语义下，空回车应视为无效输入，而不是偷偷切到 `auto`。
- **与当前分组相同不提交。**
  - 避免无意义刷新。
- **与已有分组同名允许提交。**
  - 这本质是切换到已有分组，应允许。
- **不修改数据库 schema。**
  - 新分组仍然只是 `group_name` 的新字符串值。
- **不自动重排所有分组。**
  - 保持现有 `sortGroups()` 与 `localGroupOrder` 逻辑，只在新分组首次出现时让分组列表自然纳入当前排序体系。

### 5. 对现有功能的影响

需要保持不变的现有行为：

- API 卡片布局；
- 分组标签右键菜单；
- 顶部分组拖拽排序；
- 搜索时禁用 DnD；
- 宽 query invalidation 的现有策略；
- 单个 API 卡片已有测速、开关、删除交互。

本次只在卡片右键菜单内部做局部增强，不触碰这些工作流。

## 验证方案

实施后至少验证以下场景：

1. 右键某个 API 卡片，菜单顶部出现输入框；
2. 输入一个全新的分组名并按 `Enter`，当前 API 立即切换过去；
3. 切换后顶部出现该新分组标签；
4. 输入一个已存在的分组名并按 `Enter`，效果等同于直接切换；
5. 输入空白后按 `Enter`，不发生切换；
6. 输入当前分组名后按 `Enter`，不发生重复提交；
7. 点击已有分组项，旧行为保持正常；
8. `corepack pnpm typecheck` 通过；
9. 如渲染层改动影响构建，再补 `corepack pnpm build:renderer`。
